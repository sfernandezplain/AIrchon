## pi -- Earendil Works (`github.com/earendil-works/pi`)

### Naming, shape, and why pi exists differently from the other two named targets

pi is a **monorepo** shipping three independently-versioned npm packages under `0.84.4` (as read live this session) -- `@earendil-works/pi-ai` (Unified LLM API with automatic model discovery and provider configuration -- the wire-protocol layer [llm-api-contract.md](../../references/harnesses/llm-api-contract.md) names), `@earendil-works/pi-agent-core` (Stateful agent with tool execution and event streaming -- the package that actually implements the turn loop), and `@earendil-works/pi-coding-agent` (Coding agent CLI with `bin: { pi: "dist/bundle/cli.js" }` -- the shipped harness every pi section of the book describes). Every prior citation of `pi-ai` vs. `pi-coding-agent` was already correct for its own subject matter; this section records the distinction so no reader has to resolve a seeming spelling error.

### Configuration, permissions, and hooks

**Config (VERIFIED, `configuration.md` Section 4 + `packages/coding-agent/docs/settings.md`):** **two scopes** -- global (`~/.pi/agent/`) and project (repo root) -- with **no managed/MDM tier at all** (an outlier against Claude Code's Managed and Copilot CLI's MDM layers). Merge is a stated key-by-key nested-object merge with a worked `compaction.reserveTokens` example and a named wholesale-replace exception -- `defaultTools`. The **full settings-key-cluster and CLI-flag/env-var inventory** is docs-verified rather than summarized here (the wiki page cites it explicitly rather than listing a sampled subset).

**Permissions (VERIFIED, `permissions-and-sandboxing.md` Section 5):** pi does not name its permission surface as a global `allow`/`ask`/`deny` permission table; the page cross-references the `docs/permissions.md` documented per-directory allowlist. **Hooks (VERIFIED, `hooks-lifecycle-extensibility.md` Section 5 + `packages/agent/docs/harness.md` 200KB `AgentHarness` spec):** the `AgentHarness` spec names `prepareNextTurn` as the compaction-wire hook Ch.03 already met (see Loop below), plus a `Session`-backed lane system whose deployment surface the wiki flags as an open question (imported only by `create-harness.ts` in the shipped CLI while `agent-session.ts` -- shared across interactive/print/RPC -- imports `Agent`, not `AgentHarness`).

**Observability and packaging (VERIFIED, `observability-and-self-diagnostics.md` Section 4 + `packaging-distribution-and-self-update.md` Section 4):** a real internal telemetry span schema (`@earendil-works/pi-telemetry`) with deliberately no exporter/OTel dependency shipped (backend left to caller); synthesis renumbered after pi reached 29/29 parity on those pages. Packaging is the NPm-PRIMARY outlier (the rename `@mariozechner/pi-coding-agent` -> `@earendil-works/pi-coding-agent` documented in its own synthesis), plus TUI `pi-tui` (from-scratch, dependency-free -- the fourth distinct rendering architecture alongside Ink/OpenTUI/blessed).

### Loop, memory, context, and transport

**Loop (VERIFIED, `agent-loop-implementations.md` Section 4 -- the most source-specified pi section in the book):** see the Ch.03 sequence diagram there. A turn is `turn_start` to `turn_end` (one assistant response + tool execution inside the same `turn_start`/`turn_end` pair; default `toolExecution: parallel`). The natural stop is model-driven with **no documented hard turn/budget/step cap** -- `AgentLoopConfig` has no `maxTurns`/`maxBudgetUsd`/`maxSteps` field; the only externally-forced early stop is `shouldStopAfterTurn` (an embedding-app-supplied predicate checked after `turn_end` before `prepareNextTurn`). Two harness mechanisms inject synthetic turns the same way other harnesses do, but at categorically different triggers: `prepareNextTurn` compaction wiring (see immediately below) vs. **steering queues** -- a user-queued **steering message** (Enter) drained via `getSteeringMessages()` immediately after current tool calls (before the next LLM call, without skipping those calls) and a **follow-up message** (Alt+Enter) drained via `getFollowUpMessages()` only when the agent would otherwise emit `agent_end` -- each governed by `steeringMode`/`followUpMode` (`"one-at-a-time"` default vs. `"all"`). The length-gated safety -- `failToolCallsFromTruncatedMessage()` refusing to execute any tool call when `stopReason` is `length` (output truncated by token limit) even if streaming JSON salvage made it parse cleanly -- is a second independent convergence with Hermes Agent (see below), worth naming explicitly.

**Memory and instructions (VERIFIED, `memory-management.md` Section 4 + `instruction-context-budget.md` Section 4):** pi ships **no agent-authored memory tool** (`search/code q="MEMORY.md"` zero hits; `memory`-word sweep surfaced only session-backend cognates). The persistent tier is `AGENTS.md`/`CLAUDE.md` discovery via `resource-loader.ts` with a fixed candidate list `[AGENTS.override.md, AGENTS.md, AGENTS.MD, CLAUDE.md, CLAUDE.MD]` -- **first-match-per-directory** (`AGENTS.md` always wins over a same-directory `CLAUDE.md`, at most one per directory), assembled **global first then root-most-ancestor down to cwd** (`unshift` walk producing broadest-first-nearest-last, the same shape Ch.04 documents for Claude Code by a different codebase and without either harness stating it as a design goal), with `findShadowedContextFile()` deduping a linked git worktree's main-repo file and `AGENTS.override.md` as an **exclusive per-directory substitution**. The lazy-loading companion is pi's genuinely new mechanism -- provider-native deferred-schema loading via `pi.registerTool()`/`pi.setActiveTools()` (the page's Section 5 synthesis foregrounds this as the single novel lazy-load lever the other three harnesses do not offer) -- plus programmatic control via `agentsFilesOverride` (`/virtual/AGENTS.md` synthetic-file example in `examples/sdk/07-context-files.ts`). Observability-wise, the instruction tier is delivered as a **user message after the system prompt**, matching the Claude Code docs' own troubleshooting note that `CLAUDE.md` is not part of the system prompt itself.

**Context operations (VERIFIED, `context-compression.md` Section 4 + `caching.md` Section 4 + `session-persistence.md` Section 5):** pi is the one harness of the three where the compaction wiring and caching stance are explicitly documented: compaction checks **after tools finish, before the next assistant response** at the `prepareNextTurn` hook (read directly in `resource-loader.ts` and `agent-session.ts`, confirming the hook is where the request originated -- when the completed batch would otherwise emit `agent_end`, the `prepareNextTurn` call is skipped entirely), with a documented skip condition that falls out of the source rather than being a separate flag. Caching is the shared `CacheRetention` enum across four provider protocols, with the mechanically stated convergence/inversion relative to Claude Code: pi's compaction **sets `cacheRetention: "none"`**, the opposite of Claude Code's cache-favourable stance -- flagged directly in the same `caching.md` Section 4 that documents Anthropic's breakpoint mechanics for that page. Session persistence is a JSONL-tree format (`--continue`/`--resume` plus the SDK-lane question flagged earlier), distinct from memory.

**Transport and model selection (VERIFIED, `llm-api-contract.md` Section 4 + `model-routing-and-selection.md` Section 4):** pi's wire-protocol layer (`pi-ai`) is the unified LLM API with automatic model discovery and provider configuration -- the page that names `pi-ai` correctly for what it describes is `llm-api-contract.md`, not a spelling variant to resolve, because the monorepo has both `pi-ai` and `pi-coding-agent` as real packages. Cache retention / TTL is source-verified there alongside the `pi-ai` model-family naming. Routing and auth (`model-routing-and-selection.md`, `auth-and-usage-accounting.md`) are documented at the SDK-level surface, consistent with the harness's own settings scope.

### Coordination, skills, tools, and MCP

**Coordination (VERIFIED):** pi has **no built-in orchestrator/fleet primitive** (`orchestration.md` Section 4 -- inert-by-default subagent extension, isolated at the OS-process level) and **no built-in multi-agent messaging** (`inter-agent-messaging.md` Section 4 -- the subagent extension's child closes `stdin` at spawn, so no channel exists). Fan-out is similarly **no built-in mechanism**, an official but manually-symlinked example extension spawning a genuinely separate OS process per subagent -- the fan-out page's strongest negative finding on this harness. Handoff is not native but has an example extension `handoff.ts` doing an **LLM-generated, human-reviewed context handoff into a new session** as an explicit alternative to compaction (`handoff-mechanism.md` Section 4) -- flagged as an alternative to, not a synonym of, Ch.04's compaction survival. The page also verifies that pi never implements the market-based allocation that no harness in the book implements.

**Tools and skills (VERIFIED, `built-in-tools.md` Section 4 + `built-in-skills.md` Section 4):** pi's inventory is exactly **eight built-in tools** (`grep`/`find` shell out to real `ripgrep`/`fd` binaries), and its skills surface is `agentskills.io` conformant with first-class cross-harness directory reuse -- one of the three outside-claude-code harnesses that explicitly claims that conformance (OpenCode via `.claude/skills` compatibility; Hermes Agent via `skills_list()`/`skill_view()` -- see below).

**MCP (VERIFIED, `mcp-integration.md` Section 5):** pi ships **no built-in MCP client at all**, a stated design choice -- the named gap-filler is a third-party `pi-mcp-adapter`. The wiki treats the choice as architectural (tool-surface discipline) rather than as a gap to patch silently.

## Hermes Agent -- Nous Research (`NousResearch/hermes-agent`)

### What Hermes is and why its sections read differently from the others

Unlike Claude Code and Copilot CLI (closed source) and much like OpenCode and pi (open source but read via docs plus a few targeted source files rather than a full `while`-loop read), Hermes Agent is **fully open-source Python** with three engine-owned interfaces this book verified live in source -- CLI, gateway, cron -- that funnel into one `AIAgent` class and the `agent/conversation_loop.py` body the wiki quotes as "extracted from `run_agent.AIAgent`" (`run_agent.AIAgent.run_conversation()` is now a thin forwarder). Two deliberate vocabulary clashes the wiki preserves are kept here too (the word "turn" spanning both the whole `run_conversation()` call in `conversation_loop.py`'s docstring and exactly one LLM-call-plus-tool-round in `hermes_cli/config.py`'s `resolve_turn_limit()` docstring -- an internally observed inconsistency, not a claim either module is wrong) and the `length`-gated safety that converges with pi's (see Loop below). What makes Hermes distinctive in practice is its permission surface -- **seven sandboxed terminal execution backends**, a `permissions.md` policy file, and a docs-verified tri-part backend comparison -- plus its multi-layer context handling.

### The five layers the book chooses to foreground for Hermes

**Config (VERIFIED, `configuration.md` Section 6):** Hermes ships a single `~/.hermes/` root splitting **non-secret settings** (`config.yaml`) from **credentials** (`.env`), a routing-aware `hermes config set` that writes each key to the right file, and a `hermes config migrate` step that also discovers per-skill settings -- the most explicitly split-secret-surface config story in the book.

**Permissions (VERIFIED, `permissions-and-sandboxing.md` Section 6 + corresponding entries in other pages):** the seven sandboxed terminal backends `permissions.md` policy are the enforcement surface. One concrete detail this page surfaces because it recurs elsewhere: `sandboxed-` vs. `non-` backend choice maps directly onto whether the permission layer guarantees isolation at the OS boundary or only at the prompt.

**Loop and budget (VERIFIED, `agent-loop-implementations.md` Section 5 + `conversation_loop.py`/`iteration_budget.py`/`verification_stop.py`/`kanban_stop.py` plus `hermes_cli/config.py` + `cli.py` live source):** the loop is a single `while (api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) or agent._budget_grace_call` with a thread-safe `IterationBudget` (`consume()`/`refund()` -- `execute_code` iterations are refunded so they don't eat the budget, a carve-out none of the other four harnesses documents), a one-shot `budget_grace_call` flag guaranteeing exactly one further iteration when otherwise exhausted (self-clearing; set site not determined this session), plus two interrupt/budget checks ahead of the budget on every iteration. What actually bounds `max_iterations`/`max_turns` is -- and the wiki states this openly rather than blending -- **inconsistent across files**: `hermes_cli/config.py`'s `resolve_turn_limit()` (the function whose job is to *compute* the default) states "YAML `None`/`null`/absent -> `TURN_LIMIT_UNLIMITED` -- `max_turns` is **unlimited by default**" (`TURN_LIMIT_UNLIMITED = sys.maxsize`); `cli.py` confirms via env-bridge as unlimited; against that, `iteration_budget.py`'s docstring states "the parent's cap comes from `max_iterations` (default 500)" and a defensive `getattr(..., 500)` fallback appears a second time. The subagent-tier default recurs one level down: `cli.py`'s `DEFAULT_CONFIG` sets `delegation: max_iterations: 45` while `cli-config.yaml.example` comments `default: 250` at its own `delegation: max_iterations: 250` line. None of the other three harnesses exposes enough internals to notice an equivalent inconsistency; pi's loop config has no cap field to be inconsistent about.

**Handoff vs. orchestration vs. budget (VERIFIED, `handoff-mechanism.md` Section 5 + `orchestration.md` Section 6 + `fan-out.md`):** Hermes is the one harness whose own vocabulary uses **handoff** for a different, LLM-generated context-transfer-into-a-new-session mechanism (flagged to avoid conflating with `delegate_task` parent-to-child spawning); it also ships three structurally distinct coordination layers coexisting -- an in-conversation turn-by-turn `delegate_task` that can self-nest behind an explicit `role="orchestrator"` flag, a **durable out-of-process Kanban board** that survives the spawning conversation's own death, and a cross-machine `a2a_orchestrate` layer for outside-the-local-process coordination -- with no other harness shipping a bounded equivalent to the second or third. The `delegate_task` child is a freshly constructed in-process `AIAgent` object seeded only with goal/context (never the parent's history), with only the child's structured final summary re-entering the parent while the full child transcript stays in its own session row.

**Memory, compression, and caching (VERIFIED, `memory-management.md` Section 5 + `context-compression.md` Section 5 + `caching.md` Section 5):** Hermes ships a source-verified `AGENTS.md`/`CLAUDE.md` fallthrough family for discovery -- three named cache-priority tiers (`stable`/`context`/`volatile`) over a system prompt built **at most once per session and rebuilt only on compaction** to keep `prompt_caching` warm, with a maintainer-documented fix for exactly the date-in-prompt cache-busting problem this book's [instruction-context-budget.md](../../references/harnesses/instruction-context-budget.md) leaves open for OpenCode, plus identity-slot pinning (`SOUL.md` entering at slot 1) and a dedicated **post-turn closed-learning-loop review** over `MEMORY.md`/`USER.md` with hard character caps. Compression is two independently-thresholded layers -- an 85%-of-context-length gateway safety net plus a primary `ContextEngine.should_compress()` 50% trigger -- and caching is three source layers (user docs + `agent/prompt_caching.py` vs. developer guide) that visibly **disagree** (1-hour claimed TTL vs. 5-minute actual) and on whether caching can be disabled -- the discrepancy stated rather than resolved in the harness's favour.

## DeepSeek Harness -- DeepSeek AI (`deepseek-ai/deepseek-harness`)

**Shape (VERIFIED, every DeepSeek section appended 1 September 2026 to `references/harnesses/*.md` as one-batch parity):** DeepSeek Harness is an open-source TypeScript framework on the **Cordis plugin tree** whose documented principle is **Everything is a Plugin** -- the agent loop itself is a plugin (`@deepseek-ai/dsh-agent-loop`), swappable from configuration alongside every other capability. The harness is a developer preview (September 2026); grounding here is `deepseek-ai/deepseek-harness` `docs/` + generated config/event catalogs fetched directly this session.

**Configuration, permissions, memory, and loop (VERIFIED):** configuration is the Cordis plugin enable/disable tree plus the `persona:` string under `dsh-system-prompt` (no `AGENTS.md`/`CLAUDE.md`-style convention -- the sharpest outlier of the six, already documented in `memory-management.md` Section 6 as no file convention, only a Cordis config string). Permissions vs. sandboxing is handled at the Cordis capability boundary (not an OS sandbox). Memory is no native agent-authored tool; the docs frame third-party MCP servers (Memorix, MCP Reference Memory, Engram) as default-off reference configs. The loop is a Cordis-plugin driver with waterfall/serial pre-step guard patterns rather than a single monolithic `while` (see `agent-loop-implementations.md` Section 6) -- the harness where the loop's own shape is intentionally swappable.

**Why DeepSeek matters to this book's taxonomy:** alongside deterministic orchestration (`deterministic-orchestration.md` Section 5 as the harness that lands on that page's safe-outputs seam) and the general multi-agent-coordination design space (the page's negative finding about market-based allocation), DeepSeek is the book's test of whether the harness vocabulary -- loop, memory, permission, transport -- genuinely applies to a plugin-tree harness where no single package owns "the loop" the way `pi-agent-core` does. The wiki's per-page parity table (`references/harnesses/index.md` -- 29/29 pi+Hermes, DeepSeek partial with follow-up scheduled) makes that corner explicit rather than rounding it away.
