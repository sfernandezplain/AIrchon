> What this page is: the OpenCode-specific cross-section -- how the genuinely open-source harness in the book's named three answers every mechanism generally. Where the docs are thin and source carries the claim, this synthesis says "source-verified `dev` branch" explicitly rather than blending the two.

## One-sentence shape

OpenCode is the open-source harness -- `github.com/anomalyco/opencode`, `dev` branch as the live code this book reads, `opencode.ai/docs` as the published docs -- whose docs-verified and source-verified contract is: an **eight-source `mergeConfigConcatArrays()`** hierarchy with `{env:}`/`{file:}` substitution and a granular `allow`/`ask`/`deny` + `doom_loop` permission surface implemented as **schema-omission enforcement** (not runtime refusal) with per-agent and `OPENCODE_PERMISSION` overrides, but **no OS-level sandbox** (a stated, source-verified absence, not an inference); an `--load-mode`-agnostic `instruction.ts`/`prompt.ts` surface that **re-reads `AGENTS.md` on every turn** (the strongest mid-session-edit liveness of the three named harnesses) plus a source-only nearby-file auto-attach (`resolve()`) and an invoke-only skills tier with no confirmed bundled skills; a **two-layer retry** (bounded jittered transport `packages/llm/src/route/executor.ts` wrapped by an effectively uncapped whole-turn `SessionRetry.policy` via `Effect.retry`) corroborated by issue #17648; a **unified Protocol/Endpoint/Auth/Framing route decomposition** over Anthropic Messages (`tool_use`/`tool_result`/`stop_reason` + `message_start`..`message_stop`) and OpenAI Responses (`tool_calls`/`call_id`/`finish_reason`) plus a source-verified `cache-policy.ts` auto-placement (last-tool/last-system/latest-user-message breakpoints, 4-breakpoint-cap for Anthropic/Bedrock, implicit-caching no-op for OpenAI/Gemini); a **step-limit `MAX_STEPS_PROMPT`** system-prompt injection (`packages/core/src/session/runner/max-steps.ts` -- "CRITICAL - MAXIMUM STEPS REACHED... Tools are disabled until next user input. Respond with text only" -- forcing a text-only summarization turn); a `prune()`/`process()` compaction pipeline plus a SQLite session store with `Session.fork()` and a shadow-git `SessionRevert`; a primary/subagent taxonomy (`Task` tool, `session.create(parentID)` + `task_id` resume + `deriveSubagentSessionPermission`, with a `FiberSet`-based `FiberSet.awaitEmpty` join for concurrent `Task` dispatch); and **no dedicated inter-agent message type** -- an ordinary `Info`/`Part` message row on the parent session via the directory-scoped SSE bus is the entire channel -- alongside an `agentskills.io` notes entry, a curated-until-`ecosystem.mdx` plugin surface (`opencode-supermemory` as the persistent-memory gap-filler), and a rendering stack on **OpenTUI**.

## Configuration, permissions, hooks, auth, and usage

**Config (VERIFIED, `configuration.md` Section 3 + `opencode.ai/docs`):** eight sources merged via `mergeConfigConcatArrays()` in a fixed order (source-read in `packages/opencode/src/config/config.ts`, `dev` branch). The substitution vocabulary is the mechanism to internalize: a config value can be `"{env:ENV_VAR}"` or `"{file:path}"` and is resolved before validation. The `permission` key's granular schema -- `allow`/`ask`/`deny` with glob patterns and per-agent overrides (naming an Explore/Plan/Build-style taxonomy) -- is the policy surface that compensates for the absence of an OS sandbox. A source-only `OPENCODE_PERMISSION` env-override exists (not in docs) and is flagged honestly where the wiki documents it, alongside a flagged docs/source config-key mismatch (not named here so as not to over-specify a moving `dev` branch target).

**Permissions (VERIFIED, `permissions-and-sandboxing.md` Section 3):** enforcement is **schema-omission**: whether a tool appears in the merged permission table determines whether the model can call it at all, rather than whether the harness refuses a call after the model asks. The `doom_loop` guard (a loop-detection mechanism) sits alongside the permission table as a distinct signal -- separate from `max_steps`, which guards turn-counting in Ch.03. OpenCode ships **no OS-level sandbox** -- a genuine, source-verified negative that the wiki states directly (not assumed absent). Cross-reference with [deterministic-orchestration.md](../../references/harnesses/deterministic-orchestration.md)'s `safe-outputs` immediately clarifies why: OpenCode cannot offer the job/credential-boundary stronger separation that `gh-aw`'s two-job Agentic Workflows mechanism does; its strongest enforcement is the schema itself.

**Hooks (VERIFIED, `hooks-lifecycle-extensibility.md` Section 3):** a two-surface plugin model -- a generic **`event` bus** (every lifecycle event as an untyped envelope: a real, source-verified TypeScript `Event` union in `packages/opencode/src/plugin/`) vs. a typed **`Hooks` interface** (one function per hook, typed payload -- the source-verified `Hooks` table in the same directory). The page documents the plugin's advertised capabilities and the bus-vs-interface vocabulary without re-deriving Claude Code's ~30-event catalogue; the two harnesses' hook systems are distinct primitives that share only the name "hook."

**Auth and usage (VERIFIED, `auth-and-usage-accounting.md` Section 3 + `retries.md` Section 3):** auth config is resolved via the same eight-source merge order; the usage-accounting surface is the `SessionRetry.policy`'s unbounded whole-turn retry (cross-referenced above) plus the SDK-level `/usage` surfaces the sessions layer exposes (scoped to the `Session` schema, not to a global vendor billing plane).

## Loop, memory, context, and transport

**Loop (VERIFIED, `agent-loop-implementations.md` Section 3):** the docs page `opencode.ai/docs/agents/` is thin on loop mechanics (install/config/basic, explicitly found not to describe the loop via a direct fetch) -- the real source is `github.com/anomalyco/opencode` `dev` branch. OpenCode distinguishes **primary agents** ("the main assistants you interact with") from **subagents** invoked via `Task("invoke the Task tool")`, each with per-agent permission modes. The stop condition is a documented **step limit** -- "When the limit is reached, the agent receives a special system prompt instructing it to respond with a summarization" -- and the source-verified text in `packages/core/src/session/runner/max-steps.ts` is `MAX_STEPS_PROMPT`: "CRITICAL - MAXIMUM STEPS REACHED... Tools are disabled until next user input. Respond with text only. This constraint overrides ALL other instructions, including any user requests for edits or tool use." The honest verification pointer for further reading is literal: `packages/core/src/session/` (`runner/index.ts`, `runner/llm.ts`, `runner/max-steps.ts`, `runner/model.ts`, `runner/to-llm-message.ts`) plus `session/execution.ts`, `session/compaction.ts`, `session/run-coordinator.ts` -- `dev` is not stable, so names are `dev`-branch as fetched this session.

**Memory and instructions (VERIFIED, `memory-management.md` Section 3 + `instruction-context-budget.md` Section 3):** the page's opening line is the invariant to carry forward: **no native agent-authored memory tool at all** -- the only hit for `MEMORY.md` in a docs-wide `search/code` is the third-party `opencode-supermemory` plugin in `ecosystem.mdx` (cross-referenced as the persistent-memory gap-filler, the same shape [context-retrieval-and-agentic-search.md](../../references/harnesses/context-retrieval-and-agentic-search.md) documents for RAG support). What exists is a human-authored **`AGENTS.md`** tier at project scope (root, covering its subdirectories) and global scope (`~/.config/opencode/AGENTS.md`, not committed -- recommended for personal rules), with `CLAUDE.md`/`CONTEXT.md` only as compatibility fallbacks. The liveness finding -- the one thing this harness's memory story contributes that no other harness's story does -- is **source-verified and structural**: `Instruction.system()` (read off disk) is called fresh, with no visible caching, on **every iteration of the main `while (true)` turn loop in `prompt.ts`** -- so an `AGENTS.md` edit is visible on the very next turn, with no restart, no compaction, and no command. A second, source-only finding is the nearby-file auto-attach: `instruction.ts`'s `resolve()` walks upward from the file the model just read (bounded at the project root) for the nearest `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md` not already surfaced, attached as `Instructions from: <path>` with per-message deduplication via a `claims` set -- architecturally the closest thing to Claude Code's nested-`CLAUDE.md` behaviour.

**Context operations (VERIFIED, `context-compression.md` Section 3 + `caching.md` Section 3 + `session-persistence.md` Section 3):** the compaction pipeline is **source-verified** as `prune()`/`process()` in `packages/opencode/src/session/compaction.ts` + `overflow.ts`, with an anchored-summary Markdown template, a flagged docs/source key mismatch (the one honest discrepancy the page preserves rather than silently resolving), and a `dev`-branch caveat. Caching is also source-verified -- `packages/llm/src/cache-policy.ts` (auto-placement policy: last-tool/last-system/latest-user-message breakpoints, 4-breakpoint-cap for Anthropic Messages and Bedrock Converse, implicit-caching no-op for OpenAI/Gemini), with a flagged docs/source config-surface gap. Session persistence is a `dev`-branch migration story: flat per-message JSON layout -> SQLite database, `Session.fork()` mechanics, and a shadow-git-repo-backed `SessionRevert` -- distinct from agent-authored memory.

**Transport and model selection (VERIFIED, `llm-api-contract.md` Section 3 + `streaming-and-incremental-rendering.md` + `retries.md` Section 3 + `model-routing-and-selection.md` Section 3):** the most explicitly decomposed route layer in the book -- `Protocol`/`Endpoint`/`Auth`/`Framing` as four independent axes over which Anthropic vs. OpenAI semantics are two points rather than two clients -- plus the `4-breakpoint-cap` / implicit-caching behaviour above. Retries are the bounded transport + uncapped whole-turn two-layer already named. Routing is `defaultModel()` startup-resolution (source-verified algorithm name).

## Coordination, skills, tools, and MCP

**Coordination (VERIFIED, `orchestration.md` + `handoff-mechanism.md` + `fan-out.md` + `inter-agent-messaging.md`):** **primary/subagent taxonomy** (Build/Plan/General/Explore/Scout roles -- `permission.task` glob allow/deny as schema-omission) for orchestration; **`Task` tool `session.create(parentID)` + `task_id` resume + `deriveSubagentSessionPermission`** for handoff (source-verified end to end, `dev` caveat); **`FiberSet` concurrent dispatch** (`packages/opencode/src/session/llm/native-runtime.ts` -> each batched `Task` call forks an Effect fiber; `FiberSet.awaitEmpty` joins) for fan-out; and the page's most distinctive finding -- **no dedicated inter-agent message type** -- a subagent's completion is an ordinary `Info`/`Part` row (`message.ts`/`message-v2.ts`) into the parent session observed via the directory-scoped **SSE bus** (`packages/opencode/src/server/routes/...`). General coordination-design placement: no market-based/competitive-bidding allocation; capability-based direct dispatch.

**Tools and skills (VERIFIED, `built-in-tools.md` + `built-in-skills.md` + `system-prompt-design-as-craft.md`):** the docs-confirmed tool inventory with `allow`/`ask`/`deny` plus `doom_loop`; **no confirmed bundled skills** -- purely a generic extension point for `.claude/skills` compatibility; the system-prompt assembly is source-verified at `SystemPrompt.Service`'s `environment()`/`skills()`/`mcp()` plus `prompt.ts`'s `Effect.all([...])` fixed-order concatenation, with per-agent override keying as the most granular equivalent in the book.

**MCP (VERIFIED, `mcp-integration.md` Section 3):** the most source-specified integration in the book -- `sanitize(server)_sanitize(tool)` naming, pagination, `roots`-enabled / `sampling`/`elicitation`-commented-out gap (with since-closed issues), `.well-known/opencode` org-wide remote-default servers -- plus the plugin catalogue in `ecosystem.mdx`.

## Observability, packaging, and rendering

**Observability (VERIFIED, `observability-and-self-diagnostics.md` Section 3):** the docs-confirmed `opencode logs` / structured trace surface plus a minimal flag family; the OTel cost-and-usage pipe is kept distinct (per that page's scope note).

**Packaging (VERIFIED, `packaging-distribution-and-self-update.md` Section 3):** npm-first product with manifest-plus-lockfile integrity, plus a `Session`-backed channel catalogue -- table stakes, correctly scoped.

**Rendering (VERIFIED, `tui-cli-application-architecture.md` Section 3):** **OpenTUI** as the rendering engine -- distinct from Claude Code/Copilot's Ink, pi's `pi-tui`, and Hermes' `@hermes/ink` fork -- whose component model the page describes once rather than duplicating Ch.06's reassembly/pacing concerns.
