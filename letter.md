# Determinism and Reproducible Outcomes in AI Agent Systems: A Comparative Architecture Analysis

## 1. Executive summary

"Determinism" collapses two genuinely separate engineering questions that get asked in the same breath but answered by different layers of a system:

1. **Decode-time reproducibility** — will the *same model, given the same input, produce the same tokens twice*? This is a property of the sampling/decoding layer, sits entirely on the probabilistic side of the system, and is at best a partial, conditional guarantee even when every knob is pinned.
2. **System-level guarantee** — will the *system's externally visible behaviour* (what gets written, spent, shipped, or exposed) stay within bounds regardless of what the model outputs? This is a property of the architecture wrapped around the model, has nothing to do with sampling parameters, and is where real guarantees actually live.

The interactive CLI harnesses this book covers (Claude Code, GitHub Copilot CLI, OpenCode) and the deterministic-orchestration frameworks (LangGraph, Microsoft Conductor, GitHub Agentic Workflows) sit at opposite ends of a spectrum on question 2, and none of the five say much of anything about question 1 — that's a decode-layer concern that belongs to the model-serving substrate underneath them, not to the harness itself. This document treats both questions in turn, then compares all five systems on the axis that actually matters for "guaranteeing certain results": how much of the consequential surface area sits behind a deterministic gate versus inside the model's own judgment.

## 2. Decode-time reproducibility

### 2.1 The core sampling knobs

VERIFIED (`docs.ollama.com/modelfile.md`, cited in `references/inference-engines/sampling-and-decoding-parameters.md`): a forward pass produces a probability distribution over the vocabulary, not a predetermined answer. `temperature` scales the logits before conversion to probabilities (temperature exactly `0` degenerates to greedy decoding — always the single most probable token); `top_k` and `top_p` (nucleus sampling) truncate the candidate pool before sampling; `repeat_penalty` discourages looping. Critically for this question: **`seed`** exists specifically to fix the pseudo-random generator so an otherwise-stochastic decode becomes reproducible for a given prompt and parameter set — but this is documented at the *local inference-engine* layer (Ollama), not at either hosted provider API this wiki-book has researched.

This was checked precisely rather than assumed to carry over: `references/harnesses/llm-api-contract.md` documents the Anthropic Messages API's request shape in detail — `temperature`/`top_p`/`top_k` are present — and no `seed` parameter appears anywhere in that page's content (grepped for it this session; zero matches). So for the two hosted-model contracts this book has actually sourced, decode-time reproducibility via a pinned seed is **not a confirmed capability** — it's a documented feature of local/self-hosted inference engines, not something that can be asserted about Claude Code's or Copilot CLI's own underlying model calls. BEST CURRENT UNDERSTANDING, UNCONFIRMED, offered with that label because it's a widely-known industry fact rather than something fetched this session: OpenAI's Chat Completions API has historically exposed a best-effort `seed` parameter of its own — but since that claim isn't grounded in anything this project has actually fetched and cited, treat it as background colour, not something to build a compliance argument on.

Even where a seed is honoured, reproducibility is conditional, not absolute — BEST CURRENT UNDERSTANDING, UNCONFIRMED (general ML-systems knowledge, not sourced this session against any of this book's own citations): floating-point non-associativity across batched GPU kernels, and Mixture-of-Experts routing that can vary with what else is in a serving batch, are both known sources of non-bitwise-identical output even with temperature 0 and a fixed seed on the same model weights. A seed constrains the *sampler's* randomness; it does not constrain everything upstream of the sampler.

### 2.2 Grammar-constrained decoding — a categorically different mechanism

VERIFIED (`ggml-org/llama.cpp`, `grammars/README.md` and `docs/function-calling.md`, cited in `sampling-and-decoding-parameters.md`): temperature/top-k/top-p all *reweight* the probability distribution — they never forbid a token outright. **GBNF** grammar constraints work differently: at every decoding step, the engine masks to zero probability any token that would make the output stop matching a formal grammar. This is what makes tool-call arguments reliably parse as valid JSON against a declared schema — a decode-time **guarantee of syntactic well-formedness**, independent of the model's own training reliability. The documentation is explicit that this constrains *output shape*, not *content correctness*: "the JSON schema is only used to constrain the model output and is not injected into the prompt" — the model has no idea a schema is being enforced unless you also tell it in the prompt text.

This distinction — reweighting versus forbidding, shape versus content — is the single most important thing to carry from the decode layer into the rest of this analysis, because it recurs at the system layer in a structurally identical shape (Conductor's schema validation and GitHub Agentic Workflows' `safe-outputs` schema checks are, mechanically, the same "forbid what doesn't match a declared shape" idea, just enforced a layer up, after generation rather than during it).

## 3. System-level guarantee: the deterministic/probabilistic boundary

This section is attributed throughout to **the Agentic SDLC Handbook** (Daniel Meppiel), Chapter 16, digested at `references/sdlc/16-deterministic-probabilistic-boundary.md`. As that folder's own index states, this is a single-source digest — "the handbook says," not independently cross-verified the way the wiki-book's own claims are, though the one mechanism it names (GitHub Agentic Workflows' `safe-outputs`) has been independently re-verified against GitHub's own primary docs, covered in §5.5 below.

### 3.1 Two computers, one program

The handbook's framing: an agentic system is two machines with different failure ergonomics. **The deterministic computer** — "executes the harness, runs the test suite, applies the lockfile, calls the API, writes to the filesystem... given the same inputs it produces the same outputs... when it fails it fails loudly." **The probabilistic computer** — "the model. It takes a prompt and emits a sample from a distribution... given the same inputs it produces *similar* outputs, not identical ones... when it fails it fails quietly: confident, plausible, wrong." The seam between them is where the handbook's operating rule lives: **"the model proposes; the gate disposes."**

### 3.2 Strong-form vs. weak-form supervised execution

- **Strong-form** — "the substrate denies the write capability to the agent. The agent emits buffered outputs; a deterministic post-stage applies them under filters the agent cannot bypass."
- **Weak-form** — "the prompt tells the agent to plan, then call a tool, then verify, and the agent is asked to comply." Adequate for inner-loop, recoverable, human-supervised work; not a substitute for strong-form when strong-form is available.

The handbook's rule of preference is blunt: "when the client offers strong-form, use it. Weak-form is a fallback for environments without runtime capability-based security, not a stylistic alternative." This single sentence is the yardstick the rest of this document measures every harness and framework against.

### 3.3 The four kinds of quality gate

A 2×2 matrix by **who** renders the verdict (internal to the agent vs. external) and **how** (a programmatic check vs. a judgement call):

| | Programmatic verdict | Judgement verdict |
|---|---|---|
| **Internal** | Schema validation, lint, test pass/fail, type check | Agent self-reviews its own plan against the goal |
| **External** | A fresh-context cold reader applies a rubric, pass/fail | A human checkpoint — review, sign-off |

The handbook names four concrete mismatches that each look like a gate but catch the wrong failure mode — a programmatic-internal gate (tests green) cannot catch goal drift; a judgement-internal gate cannot catch a misspelled field name; a programmatic-external rubric cannot catch a fabricated fact it never checks for; a judgement-external human reviewer rubber-stamps 200 lines of YAML they didn't actually read carefully. The selection discipline: "pick the cell that matches the failure mode you are guarding against, not the first gate that fits."

### 3.4 Named substrate patterns implementing the seam

The handbook names five worked patterns: the **safe-outputs block** (GitHub Agentic Workflows — detailed in §5.5), **CI Lambda gating** (a sandboxed CI job with a `propose-change`-only tool surface, applied by a separately-IAM-scoped Lambda after the agent exits), **Buildkite job-level secrets** (the agent's job has no deploy secret; a second, gated job holds it), **Argo Workflow with manual approval** (a `Suspend` template reifies the seam as a literal node in the DAG), and **Temporal workflow with schema-checked activities** (side-effecting activities are separately registered/versioned and only invoked when the agent's typed result satisfies the activity's input schema — replay-determinism is the substrate property that makes the seam auditable).

## 4. How the three interactive CLI harnesses actually enforce (or don't enforce) this boundary

VERIFIED against `references/harnesses/permissions-and-sandboxing.md` throughout this section.

### 4.1 Claude Code — the most layered, but the top decision layer is itself probabilistic

Claude Code's default posture is an allow/ask/deny rule engine (weak-form — a rule matched against a command string, before execution). Its **auto mode** adds a genuinely distinctive second layer: "a separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read." Worth being precise about what this is and isn't: **the classifier is itself a model** — it substitutes machine judgement for a fatigued human's rubber-stamping, but it is not a deterministic gate in the handbook's sense. It sits on the probabilistic side of the boundary, just a second, differently-trained instance of it. A first-match-wins pipeline runs rule-check → (if no rule matches) classifier → execute, with three consecutive blocks or twenty total blocks in a session pausing auto mode back to human prompts.

Underneath both of those sits Claude Code's one genuinely strong-form-adjacent mechanism: **OS-level sandboxing** (Seatbelt on macOS, bubblewrap on Linux/WSL2), independently toggleable for filesystem and network isolation. The docs state the distinction precisely: "the permission system and the classifier both reason about the command as *text* before execution; the sandbox instead constrains what the running process can actually touch... so a command that lies about its own effects... is still contained." This is the only piece of Claude Code's architecture that matches the handbook's strong-form definition — a substrate-enforced boundary that holds "regardless of what the model chose to run." But it is scoped narrowly: to what a Bash process can touch on disk and over the network, not to an arbitrary write API call the model might make through a tool the sandbox doesn't wrap (MCP servers, notably, sit outside the sandbox by default — documented elsewhere in this book's `mcp-supply-chain-trust.md`). And every escape hatch (sandbox-disabling and permission-skipping flags) is named explicitly in the docs as trading that guarantee away.

### 4.2 GitHub Copilot CLI — two rule layers, an OS sandbox, no documented classifier

Copilot CLI ships a two-layer permission architecture (an "awareness" layer and an "execution" layer) plus its own OS-level sandbox (`/sandbox`, filesystem+network policy), on by default. What this book's synthesis found is a real, sourced negative: "this session found no Copilot CLI equivalent of a classifier reviewing actions before they run — its documented model still relies on per-call rule matching plus the interactive once/session prompt, not a second model call judging intent." So Copilot CLI has the OS-enforced containment layer (strong-form-adjacent, same category as Claude Code's) but not the probabilistic pre-filter Claude Code's auto mode adds — arguably a cleaner story precisely because it doesn't blur the weak/strong-form line with a model-judged middle layer.

### 4.3 OpenCode — weakest documented guarantee of the three

OpenCode's permission engine is a real, source-verified ask/reply arbiter — but this book's own synthesis states plainly: "OpenCode's own source, read directly this session, shows no equivalent second layer at all — its permission engine is architecturally complete in itself as an approval-UX mechanism, and explicitly not framed by its own docs as a security boundary." Structurally, OpenCode's process runs with full host-process privileges once a rule allows an action; there is no OS containment layer behind it the way there is for Claude Code or Copilot CLI. In the handbook's vocabulary, OpenCode is weak-form only — every guarantee it offers depends on the rule engine correctly evaluating the request and the human correctly deciding when prompted, with nothing structural behind either.

### 4.4 The common shape, and its shared ceiling

All three CLIs converge on the same underlying idea: an allow/ask/deny rule, plus (where present) a way to reduce prompting once trust is established. None of the three implement anything resembling GitHub Agentic Workflows' capability separation — in every one of them, the *same process that runs the model's tool calls* is the process that, once approved, is trusted to execute them. That's the load-bearing structural fact this whole comparison turns on.

## 5. The deterministic-orchestration frameworks

VERIFIED against `references/harnesses/deterministic-orchestration.md` throughout (all three fetched 24 August 2026 directly from `docs.langchain.com`, `github.com/langchain-ai/*`, `github.com/microsoft/conductor`, `docs.github.com`, and `github.github.com/gh-aw`).

### 5.1 LangGraph — deterministic *control flow*, not deterministic *output*

LangGraph's own documentation names the workflows-vs-agents tension directly as a design axis: "workflows have predetermined code paths... agents are dynamic and define their own processes." Crucially, this determinism is about **which node runs next**, authored as a `StateGraph` in Python/JS — it says nothing about what any individual LLM-backed node actually outputs. A LangGraph pipeline can fix the *shape* of a pipeline with total precision while every node inside it remains exactly as probabilistic as an unstructured chat call. Its guarantees are elsewhere: **checkpointed, replayable execution** (every superstep persisted, addressable by `thread_id`/`checkpoint_id`, enabling non-destructive time-travel and forking from any historical point) and **per-node fault tolerance** (`RetryPolicy`, `NodeTimeoutError`, an error handler that can route around a failure) — both genuinely deterministic properties of the *execution engine*, not of the model. Its human-in-the-loop primitive, `interrupt()`, is a single author-placed pause point that durably suspends an entire run pending an external `Command(resume=...)` — a strong pattern for pacing human review, but it is a pause-and-ask mechanism, not a capability-removal mechanism: the node still holds whatever authority it held before the interrupt, once resumed.

### 5.2 Conductor — the same axis, plus one genuinely new idea: orchestrator-above-a-harness

Conductor's own README states its purpose in exactly the handbook's vocabulary: "repeatable, deterministic, and version-controlled... no LLM in the orchestration loop, no tokens spent deciding what runs next" — routing is a plain sequential first-match-wins scan over a YAML `routes:` list, authored declaratively rather than in code, with an offline `conductor validate` static-analysis pass with no network access. Two mechanisms are worth flagging specifically for a determinism/guarantee analysis:

- **The `validator` block** — a second LLM call grading a completed agent's output against an author-written rubric, with exactly one feedback-guided retry on failure. This is explicitly a shipped instance of the Reflexion-family grade-then-retry pattern, and it is documented as **fail-open**: "if the validator call errors or returns unparseable output, it is treated as a pass... so a flaky grader never blocks the workflow." That fail-open design is worth sitting with — it optimizes for pipeline liveness over strict enforcement, the opposite bias from a strong-form gate.
- **`budget_mode: audit` vs. `enforce`** — a genuinely disciplined staged-rollout pattern for cost guarantees specifically: run unbounded to observe cost profile, add a budget in `audit` mode (log-only), then flip to `enforce` (checkpoint-and-halt on `BudgetExceededError`) once the profile is understood. None of the three CLI harnesses' own budget mechanisms document this two-phase graduation discipline.

Conductor's field-constraint schema validation with `max_parse_recovery_attempts` is the system-layer analogue of §2.2's grammar-constrained decoding — same idea (forbid/repair anything that doesn't match a declared shape), enforced one layer up, after generation, via a correction-prompt retry loop rather than token masking during generation.

### 5.3 GitHub Agentic Workflows — the strongest documented guarantee mechanism in this entire comparison

This is the one mechanism that matches the handbook's **strong-form** definition literally, not by analogy. The agent's own job runs under a GitHub Actions token scoped to **read-only** permissions — no write permissions at all. A `safe-outputs:` frontmatter block declares which structured actions the workflow may request (30-plus handler types: `create-issue`, `create-pull-request`, `add-comment`, etc.), and the agent job **never holds a token capable of calling a write API directly** — it writes a structured JSON artifact to `$GH_AW_AGENT_OUTPUT`. A wholly separate GitHub Actions job, with a separately-scoped write-capable token, re-validates that artifact against the *live* repository state (deduplication against real open issues, schema checks against the repository's actual field definitions, a `protected-files` check, `@mention` sanitization) before making any API call at all.

The reason this is categorically stronger than every mechanism in §4 and §5.1–5.2: every other enforcement architecture in this analysis — Claude Code's classifier, OpenCode's permission engine, Conductor's `validator`, even LangGraph's `interrupt()` — gates a decision *inside one running, credential-holding process*. The process that can see the proposed action is the same process that, once approved, executes it. Safe outputs removes the write credential from the inference-holding process **entirely, at the job boundary** — the agent's own token is *incapable* of a write call regardless of what the model outputs or what prompt injection steered it, because the capability simply isn't present in that job's scope. This is precisely the handbook's own distinction restated in real infrastructure: "the claim is not 'we trust the model'... the claim is 'the model can propose any change; the substrate enforces what gets applied.'"

## 7. What this means in practice

Read together, the honest shape of "determinism" across this whole space is: **nobody has made the model itself deterministic in any way that matters for production guarantees, and the two questions from the executive summary really are independent.** A pinned seed and greedy decoding buy you *decode-layer* reproducibility for regression testing — genuinely useful for isolating "did my prompt change or did sampling just vary" — but that property isn't documented for either hosted API this book has sourced (Anthropic's or, by extension, the OpenAI-compatible surfaces these harnesses talk to), and even where it exists, it doesn't survive contact with batched GPU serving or MoE routing without qualification.

The guarantee that actually holds up is architectural, and it scales with how far the write capability sits from the process holding the model's output:

- **Weakest**: a rule engine reasoning about a command as text before it runs (OpenCode, and the rule layer of Claude Code/Copilot CLI on its own) — this is the handbook's weak-form, full stop.
- **Middle**: OS-level sandboxing that contains a process's actual I/O regardless of what the model intended (Claude Code, Copilot CLI) — strong-form for the *process boundary*, but scoped to what the sandbox wraps, and every one of these ships a named, deliberately visible bypass.
- **Middle, different axis**: deterministic *control flow* around the model (LangGraph, Conductor) — this buys you predictable pipeline shape, replayable execution history, and fine-grained fault tolerance, but says nothing on its own about whether any individual step's output is trustworthy; Conductor's own `validator` is explicitly fail-open specifically because the design prioritizes pipeline liveness.
- **Strongest documented anywhere in this book**: job/credential-boundary capability separation (GitHub Agentic Workflows' `safe-outputs`) — the only mechanism in this entire comparison where the guarantee doesn't depend on any rule, classifier, or grader getting the judgement call right, because the capability to act on a wrong judgement simply doesn't exist in the process making it.

The handbook's own three-habit discipline (§3.4) is, on this evidence, the right lens for choosing among these rather than treating any one harness as categorically "more deterministic": draw the deterministic/probabilistic line on the diagram before writing the prompt, pick the gate cell that matches the specific failure mode you're guarding against rather than the first one available, and — the sharpest of the three — refuse the write token whenever a strong-form alternative exists, treating an in-process permission classifier or a fail-open validator as a documented, named compromise rather than a substitute for capability separation.
